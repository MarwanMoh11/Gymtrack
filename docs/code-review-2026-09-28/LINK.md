## Findings

### LINK-01: A Finish tapped on the phone permanently loses wrist-logged sets that are still in the delivery queue
- Severity: P1
- Category: bug
- Confidence: likely (the code path is traced end to end; the trigger is WatchConnectivity delivering the queued transfer late, which is the same premise GT-002 rests on)
- Location: `GymTrack/Models/SessionClosing.swift:60-69` (`close`), `GymTrack/Services/ActiveWorkout.swift:855-871` (`finish`), `GymTrack/Services/WatchCommandCenter.swift:82-85` and `:359-361` (`.logSet`, `setLog`), `GymTrack/Services/ActiveWorkout.swift:989-990`, `GymTrack/Services/WatchCommandCenter.swift:188-193`, `GymTrackWatch/WatchConnector.swift:307-316` (`reconcile(with: nil)`)
- What happens: `close` deletes every row that is not completed (`for set in sets where !set.isCompleted { context.delete(set) }`). A wrist log that has not arrived yet is exactly such a row. When the queued `.logSet` lands later, `setLog(id:)` searches only the active session, and `ActiveWorkout.apply` returns `true` for an unknown set ID, so the log is dropped silently. The ended mirror then reaches the watch, and `reconcile(with: nil)` runs `pending.clear()`, which throws away the wrist's only copy. The finish batch that would have saved these sets is sent only when the wrist is the one that finishes. When the wrist's Finish lands after the phone has closed the session, `WatchCommandCenter.swift:188-193` applies only the metrics and ignores `batch.logs`.
- Failure scenario: The phone is in a locker. The lifter logs the last 3 sets on the wrist, and they queue through `transferUserInfo` (the watch footer says sets are waiting). The lifter walks back, opens the phone app, sees those 3 rows unlogged ("3 sets not logged, they'll be dropped from the record") and assumes the watch will sync, then taps Finish before the queue has flushed. The 3 rows are deleted, the queued logs arrive and are dropped, and the watch clears its pending logs. Three real sets are missing from the record, from Health activity metadata and from the export.
- Suggested fix: (1) For a watch-driven session with a reachable watch, have the phone's `ActiveWorkout.finish` ask the watch for its `WatchFinishBatch`: a new `WatchCommand`/mirror request answered via `sendMessage` reply, with about a 2 s timeout. Apply the batch with `applyWatchFinish` before `close`. (2) Make late logs attach to the identified finished session, as GT-002 itself suggested. Keep an in-memory map, per recently closed session, of the rows `close` deleted (id, catalogID, name, order, index, tracking, targets). A late `.logSet` whose ID is in that map and whose `at` is at or before `endedAt` then recreates the row as completed. It is in memory only, so rows nobody lifted still leave no trace. (3) On the watch, when the ended mirror names the pending session as `.finished`, send the remaining batch as a late `finishSession` instead of clearing it. On the phone, apply a batch to a just-closed session through the mechanism in (2) instead of discarding it at `WatchCommandCenter.swift:188-193`.
- Verify by: Extend `Tests/WatchCommandReliabilityTests.swift` with an in-memory store. Run `close` first, then the late `.logSet` through the headless handler and through `RootView`'s route, and expect the set to be present and completed with the wrist's `at`. Manual check: with the watch in airplane mode, log 2 sets, finish on the phone, then re-enable the watch's connection. The sets must appear in the summary.

### LINK-02: The phone's first mirror after a relaunch says "no session", so the watch ends and discards its Health recording mid-workout
- Severity: P1
- Category: bug
- Confidence: likely (the phone side is confirmed; the watch reaction is traced through `WatchRootView.syncRecorder`, and whether the transient nil gets rendered depends on the watch's render timing)
- Location: `GymTrack/Services/WatchBridge.swift:169-176` (`activationDidCompleteWith` calls `push()`), `:109-125` (`push`), `:34-37` (initial `idle = .empty`, `sessionSnapshot = nil`), `GymTrack/App/GymTrackApp.swift:64-77`, `GymTrack/Services/WatchCommandCenter.swift:313-321` (`pushMirror` pushes idle before session); watch side `GymTrackWatch/Views/WatchRootView.swift:93-115`, `GymTrackWatch/WatchConnector.swift:307-316`
- What happens: `WatchCommandCenter.configure` activates the session at launch. When activation completes, the bridge `push()`es whatever it holds, which in a fresh process is `idle: .empty, session: nil, endedSession: nil`, stamped `sentAt: .now`. Nothing has told the bridge the session yet: no RootView exists in a background launch, and in a foreground launch `.task` may run after activation. The watch accepts the mirror because it is newer and reads `session == nil`. `syncRecorder` then sees a running recorder with no matching `endedSession`, so it calls `recorder.end(discardingSamples: true)`, and `reconcile(with: nil)` clears the pending overlay and the rating outbox. The real mirror follows milliseconds later (`pushMirror` → `update(session:)`). By then the recording is gone or ending. `startIfNeeded` may even return early because `isRunning` is still true while `end` is awaiting, which leaves nothing recording.
- Failure scenario: Mid-workout, iOS jetsams GymTrack in the background (the camera or another heavy app was used between sets). The next wrist log wakes the app in the background. The activation push says no session, the watch discards the Health workout it has recorded since the start, then restarts or fails to restart it. The session's Health workout loses its heart rate and energy up to that point, or is lost entirely. The same thing happens when the user cold-opens the phone app mid-workout. The watch's idle screen also flashes the empty placeholder ("hasn't sent today's plan").
- Suggested fix: Never push state the phone has not established. Give `WatchBridge` a `hasState` flag set by the first `update(idle:)`/`update(session:)`, and have `activationDidCompleteWith` push only when it is set. In `WatchCommandCenter.configure`, seed the bridge from the store right after `activate()` by calling `pushMirror(context:)` once. In `pushMirror`, set the session before the idle so no intermediate nil-session mirror is sent (`WatchCommandCenter.swift:316-319`).
- Verify by: A unit check that a fresh `WatchBridge` produces no payload before `update` is called. Manual check on paired sims: start on the wrist, `simctl terminate` the phone app, log a set on the wrist, then confirm the watch keeps its recorder (same `recorder.sessionID`, not restarted) and that the final Health workout spans the whole session.

### LINK-03: Stale sessions are closed only on a cold launch, so a forgotten session blocks every wrist Start and a warm Finish writes an all-night workout to the record and Health
- Severity: P1
- Category: bug
- Confidence: confirmed
- Location: `GymTrack/App/RootView.swift:463-494` (`resumeUnfinishedSession`, the only 12-hour check, at :477, reached only from `.task` at :37-46), `GymTrack/App/RootView.swift:388-396` (`startFromWatch`), `GymTrack/Services/WatchCommandCenter.swift:60-67` (headless start), `GymTrackWatch/WatchConnector.swift:76` (watch hides sessions older than 12 h), `GymTrack/Models/SessionClosing.swift:60` (`close(at: .now)`), `GymTrack/Services/HealthKitService.swift:162-164`
- What happens: The "older than 12 hours" rule runs only in `.task`, which fires once per RootView lifetime and never in a background launch. The fixes from f5809ff made the watch refuse any session older than 12 h (`guard session.startedAt.timeIntervalSinceNow > -12 * 3600 else { return nil }`). Both phone start routes answer a start with the existing session (`if let activeWorkout { activeWorkout.pushToWatch(); WatchBridge.shared.resend(); return }` and `guard activeSession(in: context) == nil else { pushMirror…; return }`), so the wrist is handed a session it will not draw. Separately, a warm-resumed stale session finished from the phone goes through `close(in:)` with `.now`, which is the "workout that ran all night" `close(at:)` was written to prevent. `saveWorkout` then writes `startedAt…endedAt` to Health.
- Failure scenario: The lifter forgets to finish yesterday's session, and the app stays suspended overnight, or is terminated and only woken in the background by the watch. The next morning they tap Start on the watch. It shows "Starting… your phone is building the session" for 8 s and falls back to idle, on every attempt. Opening the phone (warm) shows yesterday's workout still running. Tapping Finish records a roughly 20-hour session in the export and a 20-hour strength workout in Health.
- Suggested fix: Move the rule into one shared helper, for example `WorkoutSession.isStale` plus a `closeIfStale(in:)` that does the delete-or-`close(at: lastLogged)` from `resumeUnfinishedSession`. Call it from `startFromWatch` and headless `.startToday`/`.startFreestyle` before the "already running" check, from `activeSession(in:)`/`pushMirror`, and from RootView's `scenePhase == .active` handler, so a warm resume applies it too.
- Verify by: A harness test for the helper (13 h old with sets closes at the last set, empty deletes). Manual check: seed a session with `startedAt` 13 h ago, keep the app resident, send a wrist Start, and expect a new session on the wrist. Resume the app and expect no stale dock.

### LINK-04: Stale live metrics delivered after the finish overwrite the session's final heart rate and energy
- Severity: P2
- Category: data-rule
- Confidence: likely
- Location: `GymTrack/App/RootView.swift:351-354, 416-431` (`applyLateMetrics`), `GymTrack/Services/WatchCommandCenter.swift:226-232, 262-271` (`.metrics`, `apply`), `GymTrack/Services/WatchBridge.swift:146-149`, `GymTrackShared/WatchLink.swift:283-292`; source `GymTrackWatch/WatchWorkoutRecorder.swift:213-217` with `GymTrackWatch/WatchConnector.swift:168-191`
- What happens: The watch sends `.metrics` every 5 s through `send`, which falls back to `transferUserInfo` when the phone is unreachable or a `sendMessage` fails, so a backlog of partial snapshots can build up. The final metrics travel with `finishSession` over `sendMessage`. The two channels are not ordered, so queued partials can land after the finals. For a closed session, both store writers overwrite the finals unconditionally: `session.averageHeartRate = average`, `session.maxHeartRate = max` (not even a max-merge), and `activeEnergyKcal = energy`. The headless case's comment says it only keeps metrics for a session that has already closed, but `:230` also writes to the *active* session, and saves, every 5 s.
- Failure scenario: The phone sits in a locker for 30 minutes, so about 360 metrics snapshots queue. The lifter walks back and, while the queue is draining, taps Finish on the wrist. The finals (average 142, max 178, 410 kcal, plus the Health workout ID) arrive over `sendMessage` and are applied. Then the backlog drains and each partial overwrites them, ending at something like average 128, max 161, 190 kcal. The export and the summary show those numbers as the session's measured totals, while the watch's Health workout disagrees. The drain also means hundreds of main-thread saves and full fetches.
- Suggested fix: Make live metrics non-durable. In `WatchConnector.send`, never fall back to `transferUserInfo` for `.metrics` unless it carries `healthWorkoutID` (the handover). On the phone, for a session that is not active, accept `.metrics` only when it carries `healthWorkoutID`, and never write partials into an active session headlessly. Better still, add an optional `sampledAt: Date?` to `WatchWorkoutMetrics` (it decodes as nil from older builds) and have `merging`, `apply` and `applyLateMetrics` ignore anything older than what they already hold.
- Verify by: A test that applies the finals, then an older partial for the same finished session, through both `applyLateMetrics` and the headless `.metrics` route, and expects the finals to survive. The same test should confirm that an active session is not written headlessly.

### LINK-05: A wrist undo can be overtaken by its own log, and a repeated log re-runs `complete()`, so a taken-back set returns to the record
- Severity: P2
- Category: data-rule
- Confidence: likely (depends on cross-channel reordering or sendMessage-then-requeue duplication, which `RootView.swift:389-391` already acknowledges happens)
- Location: `GymTrack/Services/ActiveWorkout.swift:989-997` (`apply(.logSet)`, with no already-completed or stamp check), `:254-305` (`complete`: `recordLoadNudge(.declined…)` at :274, `lastLoggedSetID = set.id` at :265, `carryLoadForward`, `restTimer.restore`), `GymTrack/Services/WatchCommandCenter.swift:82-106, 147-157`, `GymTrackWatch/WatchConnector.swift:183-190` (requeue on error), `:331` (a pending undo is kept but never re-sent)
- What happens: `.logSet` and `.undoSet` carry no ordering information that the phone checks, and the phone applies whichever arrives last. A log that went into the userInfo queue (the phone was unreachable, or `sendMessage` errored and was requeued) can arrive after an undo sent a moment later over `sendMessage`. The undo then lands on an incomplete row and does nothing, and the log completes the set. The watch keeps its undo pending (`pending.undos.filter { sets[$0]?.isCompleted == true }`) but never re-sends it, so the two screens disagree until a wrist Finish replays it. A Finish on the phone keeps the mis-tap. On the UI route, even a plain duplicate `.logSet` for an already-completed set re-runs `complete()`. That records the standing load nudge as `.declined` although nobody declined it, moves the effort question back to the older set, pushes the old load onto rows the lifter has since re-dialled, and can put the app back into a rest mid-set. The reverse race exists too: a wrist log that the phone confirms and the lifter then undoes *on the phone* before the confirming mirror reaches the watch stays in `pending.logs`, and a later wrist Finish re-logs it through `applyWatchFinish`.
- Failure scenario: The phone app is terminated in a bag. The lifter mis-taps Log on the wrist, the `sendMessage` that wakes the phone errors, and the log is requeued. Two seconds later they tap Undo, which is delivered live. The queued log then lands. The phone shows the set as logged and the wrist shows it undone. The lifter finishes on the phone, and a set that never happened is in the record.
- Suggested fix: On the phone, treat a `.logSet` whose set is already completed with the same `completedAt` as a no-op that only pushes the mirror. Do this in `ActiveWorkout.apply` and in the headless case. Carry the undone completion stamp in the undo (`undoSet(id:, completedAt: Date?)`, where the optional keeps older payloads decoding). The watch should re-send a pending undo when a mirror shows the set completed at that same stamp, the way `WatchRatingOutbox.reconcile` already re-sends ratings, and the phone should refuse a `.logSet` whose `at` equals a stamp an undo already took back in this session (an in-memory set, so nothing persists).
- Verify by: A routing test covering undo then log with the same stamp (expect not completed after the wrist reconciles), duplicate log after a rating that produced a nudge (expect no `.declined` and an unchanged `lastLoggedSetID`), and duplicate log after the next set's weight was changed (expect the weight unchanged).

### LINK-06: A start queued while the phone is out of range has no expiry and starts a workout whenever it lands
- Severity: P3
- Category: bug
- Confidence: likely
- Location: `GymTrackShared/WatchLink.swift:320-321` (`startToday`/`startFreestyle` carry nothing), `GymTrack/Services/WatchCommandCenter.swift:60-80`, `GymTrack/App/RootView.swift:308-328, 388-411`; watch `GymTrackWatch/Views/WatchIdleView.swift:157-159, 180-190`
- What happens: The watch promises "It starts the session as soon as it's back", then drops its Starting state after 8 s. The phone applies the queued start whenever the transfer arrives, with no stamp to judge its age. A reply-timeout requeue (`WatchConnector.swift:183-187`) can likewise deliver a second copy after the first session has already finished over `sendMessage`, which starts a new session straight away. The watch then receives a session mirror and `startIfNeeded` begins an `HKWorkoutSession`.
- Failure scenario: The lifter taps Start with the phone at home, gives up, and trains without the app. Hours later the phone comes back in range and a workout starts on the phone and the wrist. The wrist records heart rate until someone notices. If the lifter taps Finish rather than Discard, a phantom Health workout is saved.
- Suggested fix: Stamp starts (`startToday(at: Date?)`; a missing stamp decodes as nil for old payloads) and have both routes refuse a start older than a few minutes. They should reply with the current mirror, as they already do for a start that finds a session running.
- Verify by: A routing test with a start stamped 10 minutes ago, expecting no session to be inserted. Manual check: queue a start with the phone unreachable, wait, reconnect, and expect no workout.

### LINK-07: The headless mirror states "no rest" as fact, which clears the rest running on the wrist
- Severity: P3
- Category: bug
- Confidence: likely
- Location: `GymTrack/Services/WatchCommandCenter.swift:326-328` (`rest: (nil, nil, 0)`); watch `GymTrackWatch/Views/WatchRootView.swift:73-75`, `GymTrackWatch/WatchRestTimer.swift:51-57`
- What happens: The headless path deliberately starts no rest, because the wrist's rest is meant to be the one that counts. But its mirror says `restEndsAt: nil`, and the watch treats a nil that follows a non-nil value, arriving more than 3 s after a local start, as "skipped on the phone" and calls `clear()`.
- Failure scenario: The phone app was up with a rest that was still in its last mirror (suspended before the rest ended), then it was killed. The lifter logs a set on the wrist and a local rest starts. The phone's background launch takes more than 3 s, its headless mirror says no rest, and the wrist countdown vanishes mid-rest.
- Suggested fix: In `pushMirror`, derive the rest the same way `ActiveWorkout.complete` does: find the last completed set, and if `completedAt + restSeconds` is still ahead and `restAutoStart` is on, send that as `restEndsAt`. Otherwise send nil.
- Verify by: A snapshot test of `pushMirror`'s rest for a set completed 20 s ago with a 90 s rest. Manual check on sims: terminate the phone app mid-rest, log a set on the wrist, and the rest should keep counting.

### LINK-08: Every headless command refetches the whole history, unfiltered, several times, and rebuilds per-exercise history on each push
- Severity: P3
- Category: performance
- Confidence: confirmed
- Location: `GymTrack/Services/WatchCommandCenter.swift:340-361` (`allSessions` with no predicate, called by `activeSession`, `session(id:)`, `setLog`), `:313-336` (`pushMirror`: another `allSessions`, all `Plan`s, all `PlanDay`s, `WatchMirrorBuilder.idle` with its streak, and `TrainingStats.lastPerformance` per exercise, which sorts every session each time), `:226-232` (a save every 5 s for metrics)
- What happens: A single headless `.logSet` runs at least two full `WorkoutSession` fetches, each followed by the overlap scan, plus `PlanDay` and `Plan` fetches and E × (sort all sessions + walk sets). For an exercise with little history, that faults the sets of every past session. `ActiveWorkout` caches the same data once per session (`ActiveWorkout.swift:118-122`), and the headless path does it on every command, inside the limited time iOS allows a background WatchConnectivity launch.
- Failure scenario: With 2 years of history (about 400 sessions × 20 sets) and a session that includes a new exercise, each wrist tap in headless mode faults thousands of `SetLog`s. The mirror comes back late, which also widens the race windows in LINK-02, LINK-05 and LINK-07.
- Suggested fix: Fetch the active session with `#Predicate<WorkoutSession> { $0.endedAt == nil }`. Look up a set by ID with a `SetLog` predicate. Cache the per-session `lastTimeLabel`/rest lookups keyed by session ID, the way `ActiveWorkout` does, and invalidate them when the session changes. Run `WatchSessionRecovery` once per process, not on every fetch.
- Verify by: Instrument a headless `.logSet` against the seeded store (`-GTSeedSampleData`) plus synthetic history, and time it before and after.

### LINK-09: The headless path keeps a second, process-lifetime ModelContext on the same store as the UI
- Severity: P3
- Category: code-health
- Confidence: speculative
- Location: `GymTrack/Services/WatchCommandCenter.swift:26-27` (`lazy var context = ModelContext(container)`), used whenever RootView returns false (`RootView.swift:337-338, 349, 357, 369, 379-381`)
- What happens: Both contexts are `@MainActor`, so the second one adds nothing except a separately cached copy of the same rows. When the UI finishes a session in `mainContext`, a later fall-through (`.requestMirror` with no workout on screen, or a `.rateSet` for a finished session) fetches in the headless context. Whether its already-registered `WorkoutSession` sees the new `endedAt` depends on SwiftData merging saves across sibling contexts, which was unreliable on some iOS 17 and 18 builds. If it does not merge, `pushMirror` would republish a finished session as live, and the watch would start recording it.
- Failure scenario: (Unconfirmed.) A session is started headless, the app is foregrounded and the session is finished on the phone. The wrist raises and sends `requestMirror`, the headless context still sees `endedAt == nil`, and it pushes the finished session as active.
- Suggested fix: Use `container.mainContext` in `WatchCommandCenter`. It is already on the main actor, and the change also lets `@Query` see headless writes without the store re-read workaround in `startFromWatch` (`RootView.swift:397-399`).
- Verify by: A harness with two `ModelContext`s on one container: load a session in context A, set `endedAt` and save in context B, refetch in A, and check `endedAt` on the iOS 17.0 and 18.0 simulators.

### LINK-10: No test drives the command routing, so the GT-001 and GT-002 verifications were never automated
- Severity: P3
- Category: test-gap
- Confidence: confirmed
- Location: `Tests/WatchCommandReliabilityTests.swift` (covers only encoding, `WatchPendingActions`, `merging`, and `applyWatchFinish` plus `close` on the model), with nothing for `WatchCommandCenter.applyHeadless` or `RootView.handleWatchCommand`
- What happens: GT-001 asks to "verify with a delayed command from A after starting B", and GT-002 asks to "test both message arrival orders" through the real handlers. Neither routing function is exercised, so LINK-01, LINK-04 and LINK-05 are invisible to the suite.
- Suggested fix: Extract the headless decision logic into a pure `WatchCommandApplier` that takes a `ModelContext` and returns mirror or side-effect intents, and keep `WatchBridge`, HealthKit and Live Activity out of it. Then cover delayed Finish/Discard for A while B runs, a late log after a phone Finish, undo overtaken by log, stale metrics after the finals, and a stale or duplicate start.
- Verify by: The new script fails against the current code for LINK-01, LINK-04 and LINK-05 and passes after the fixes.
